# Fork feature inventory and v0.3.0 migration plan

> Status: initial source audit, 2026-11-06  
> Baseline: upstream tag `v0.3.0` (commit `68734926a981301ead72b204f13e2be083845067`)  
> Fork source audited: `main` at the time of this document  
> This document is a living engineering record. Update the decision/status and validation notes whenever a feature is ported or its design changes.

## 1. Why this document exists

The fork's controller and iOS work is a collection of cooperating features, not a patch that can safely be replayed wholesale onto v0.3.0. The fork has 20 commits beyond the merge base and changes more than 50 paths. Upstream v0.3.0 has substantially reorganized the application, player input, target selection, cursor, UI script and plugin systems.

The migration rule is therefore:

1. Preserve v0.3.0 as the architectural base.
2. Understand each fork feature in terms of user-visible behavior, state ownership, data flow and integration seams.
3. Reuse assets/addon logic where its host APIs still exist.
4. Reimplement core integration against v0.3.0's current modules instead of copying old files.
5. Record implementation choices and tests here as work progresses.

Do not treat a successful compile as proof of behavioral parity. In particular, controller stance action-slot selection must be verified for both the icon shown and the action actually invoked.

## 3. Old implementation: architecture and data flow

### 3.1 Input acquisition and normalized state

The old `gamepad.rs` owns a Bevy resource, `GamepadState`. It stores:

- Connection state.
- Left/right stick vectors and trigger magnitudes.
- Face, shoulder, system, stick-click and D-pad button states.
- Previous-frame button/trigger state, allowing pressed/released edge detection.
- Virtual mouse coordinates and click state.
- Touch movement stick ownership/state and touch-look delta/ownership state.

Desktop polling uses SDL3. The SDL handle is held as a Bevy non-send resource because SDL objects are not Send/Sync on macOS. Initialization is deliberately performed before `App::run()`, not in a Startup system, to avoid macOS event-loop reentrancy. iOS uses `objc2_game_controller::GCController` and its extended gamepad instead of SDL.

The common state abstraction is important: downstream bindings, movement, camera, targeting and Lua do not need to know whether input came from SDL, Apple's GameController API, or a touch gesture. Preserve this separation in the port.

### 3.2 Core plugin integration

The old `GamepadPlugin`:

- Initializes `GamepadState`.
- Polls input before `BindingsPlugin::BindingSet`.
- Synchronizes a snapshot to Lua after polling.
- Runs R3 target and utility binding logic in explicit order relative to binding/script-call systems.
- Runs right-trigger interaction.
- Adds opt-in debug overlay and iOS diagnostics.

Ordering is behavioral, not cosmetic: bindings must see this frame's controller state; Lua must see the same snapshot; target/interaction actions must be ordered consistently with the UI script and target systems.

### 3.3 Binding engine and action layers

The old `bindings.rs` integrates controller buttons into the same chord/command dispatch machinery used by keyboard bindings. The controller mapping is:

- Face buttons: A/B/X/Y → controller slots 1–4.
- D-pad: Up/Down/Left/Right → slots 5–8.
- No modifier: action slots 1–8.
- L shoulder held: slots 9–16.
- R shoulder held: slots 17–24.

L/R are hold modifiers. The modifier is captured when a button is pressed so a later shoulder change does not mutate the meaning of an already-held button. The controller bar addon displays the corresponding layer. The user's intended ergonomics are preserved: no extra held modifier for the face/D-pad group; L/R provide the two extra action layers.

The binding engine also needs reliable release handling, focus/UI-consumed input gating, and stuck-latch cleanup. A port must not implement a second independent action dispatch path that bypasses rebinding.

### 3.4 Controller bar addon and stance mapping

`BenillaController` is a FrameXML addon that displays eight ActionButton-style buttons. Its physical layout mirrors the controller: Y/X/B/A and D-pad. It displays 24 possible actions in three layers:

- Base: slots 1–8.
- L: slots 9–16.
- R: slots 17–24.

The bar does not change the game's action-bar page when the user holds L/R. It resolves each displayed button to an action slot and uses `UseAction` when invoked. The modifier layer mapping is fixed: controller slot +8 for L, +16 for R.

The base layer is stance-aware. In this fork, `GetBonusBarOffset()` is a page index rather than the stock action-slot offset. The addon maps page 0 to slots 1–8 and nonzero page N to `60 + N * 12 + controllerSlot`. The same resolver must be used for both icon rendering and button activation.

A previous bug demonstrated why this matters: the displayed eight icons followed the stance, but pressing a button still activated Action Bar 1. The later fix routes the actual press through the same stance-aware resolver. This is a release-blocking regression test for the migration.

### 3.5 Mobile addon and touch ownership

`BenillaMobile` is a Lua addon with a 4-column × 3-row action bar. It pages through up to 120 action slots (10 pages), reads existing WoW action slots and invokes `UseAction`; it is not a separate spell/action system. It supports resizing, repositioning, cooldown display, drag/drop and lock/unlock commands.

The virtual movement stick is split deliberately across addon and core:

- The addon owns the joystick art, position, radius, thumb travel and saved settings.
- The core owns touch hit-testing and finger capture.
- A finger captured by the movement stick controls movement without stealing another finger's ability to tap UI.
- The addon hides its virtual stick when a physical gamepad is connected.

The addon calls `Gamepad_IsTouchDevice`, `Gamepad_IsConnected` and `Gamepad_SetTouchStick`. Those are required host APIs, not optional decorative helpers. Do not claim the addon is portable until the bridge and multi-touch capture path are present.

The core state also has an independent touch-look gesture: world-area drag deltas feed camera look, while UI taps remain UI interactions.

### 3.6 Cursor, camera, movement, swim

The controller feature set is integrated into existing gameplay paths rather than implemented as a standalone camera/player:

- Virtual cursor position is used as the effective pointer position for world/UI hit testing.
- LT/ZL plus A/B synthesizes virtual left/right clicks in the old camera world-mouse latch.
- Right stick contributes to camera look; a trigger modifier can suppress camera look while virtual mouse mode is active.
- Left stick is merged with keyboard movement into the same movement axes calculation.
- L3 toggles autorun.
- Swim movement uses the same analog movement axes; right-stick pitch drives the mover pitch with special near-surface handling to avoid accidental diving while ordinary camera pitch is downward.
- Touch movement and touch look have separate ownership so the two gestures do not fight each other.

These features touch core state and scheduling. Reimplement them in the v0.3.0 equivalents; do not transplant the old `player/controller.rs`, `player/input.rs`, `player/swim.rs`, or camera files as a unit.

### 3.7 Targeting and interaction

The old controller-specific targeting layer is built on the target subsystem. The intended controls include R3 target selection, modifier-dependent friendly/interactable selection, Smart behavior outside combat, and RT interaction with the resolved interaction/selection target.

The old fork also changed `target/scan.rs` and `target/hover.rs`, so the final behavior is not isolated to `gamepad.rs`. During porting, distinguish controller-triggered selection from the general target/hover changes in the fork. Preserve only the behavior actually required by controller use, unless a separate target improvement is intentionally adopted.

### 3.8 Lua gamepad API

The old `benilla-ui/src/script/gamepad.rs` registers Lua globals for querying:

- `Gamepad_IsConnected()`
- `Gamepad_IsButtonDown(button)`
- `Gamepad_GetAxis(axis)`
- `Gamepad_IsTouchDevice()`
- `Gamepad_SetTouchStick(x, y, radius, travel, enabled, unlocked)`

The state is copied into the UI script model, so addon Lua reads a stable frame snapshot rather than accessing Bevy resources directly. The v0.3.0 port should keep this boundary: script-facing API in `benilla-ui`, acquisition and ECS state in the app layer.

### 3.9 iOS build and runtime

The fork adds an iOS Info.plist and `scripts/ios-package.sh`. The script builds `aarch64-apple-ios`, creates a `.app` directory, copies the binary and plist, optionally bundles WoW Data and AddOns, sets bundle metadata, validates provisioning-profile expiration and bundle ID, signs/verifies the app, and optionally installs it through `devicectl`.

The packaging script is operational infrastructure, separate from the runtime GameController implementation. Keep it independent where possible, but verify its binary path, bundle layout, minimum OS/device requirements and signing behavior against the current v0.3.0 build.

## 4. v0.3.0 integration map

The v0.3.0 tree has materially different seams:

- Application composition is organized through the current game plugin group and ordered plugin registration.
- Player input and movement live in the current player subsystem; old monolithic assumptions about system parameters and resources do not carry over.
- Target selection and hover are split into smaller modules and have different scan/pick interfaces.
- Cursor and pointer ownership are part of the current cursor/UI pipeline.
- UI script state is model-backed and installed through the current script plugin architecture.
- The current crate exposes `run_with(build, extend)` for adding an extension to a built app, but use this only where the required state and scheduling seams are public and sufficient. It is not a substitute for integration when a feature must participate in private player/target internals.

Before adding code, inspect the exact v0.3.0 definitions and plugin ordering at the target seam. Do not infer compatibility from matching filenames.

## 5. Porting decisions and work sequence

### Phase A — Preserve portable assets

1. `MinimapMover`: compare its calls against v0.3.0 FrameXML; reuse if API-compatible.
2. `BenillaMobile` action-bar UI: retain its 4×3 paging and existing-action-slot model; validate all FrameXML globals/templates.
3. `BenillaController` visual bar: retain layout, cooldown/range/count presentation and slash commands; port only the required Lua/core bridge and ensure display/activation share one slot resolver.
4. iOS plist/package script: keep as a separate packaging layer; validate against current target output.

### Phase B — Restore the input contract

1. Define one platform-neutral controller state and edge model.
2. Implement SDL3 desktop acquisition and iOS GameController acquisition behind platform-specific adapters.
3. Add the Lua model snapshot and documented globals.
4. Establish plugin registration and explicit ordering relative to bindings, player input, UI script, cursor and target systems.
5. Test disconnect/reconnect and release-edge behavior; a disconnected controller must not leave stuck buttons or touch ownership behind.

### Phase C — Port gameplay behavior

1. Binding layers and remapping.
2. Stance-aware base action slots, fixed L/R layers.
3. Analog movement and autorun.
4. Camera look and virtual cursor/clicks.
5. Touch movement and independent touch-look.
6. Swim pitch/surface handling and horizontal strafe.
7. R3 targeting variants and RT interaction.

Each feature should be a separate, reviewable change with focused tests. Avoid one large port commit.

### Phase D — Validation

Minimum acceptance checks:

- Desktop SDL controller connects, disconnects, reconnects; every button/axis and trigger reports correct state.
- Press/release edges fire once; held modifiers are latched consistently.
- Rebinding controller slots works through the existing binding system.
- Controller bar shows and activates the same action for base, L and R layers.
- Warrior stance/form changes update base slots 1–8; L/R slots remain 9–24 and do not shift.
- L3 autorun toggles once per press.
- Analog movement, camera look, virtual cursor and synthetic clicks work without breaking physical mouse/keyboard.
- R3 target behavior and RT interaction use the intended target and do not trigger UI/world actions accidentally.
- Underwater pitch, near-surface behavior and left-stick horizontal strafe are verified.
- Touch stick owns only its finger; a second finger can still use the UI. Physical controller connection hides the touch stick.
- iOS arm64 build, app bundle, signing and install are tested independently of desktop CI.
- Existing v0.3.0 unit/integration tests remain green.
