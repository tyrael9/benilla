# v0.3.0 addon and controller integration audit

> Branch: `work/v030-addon-compat-audit`  
> Baseline: `upgrade/v0.3.0`  
> Status: native integration is implemented; compile, full-matrix and hardware validation remain gates.

## CI strategy

The pull-request fast lane checks formatting, message catalog and pass-span rules, runs the focused `benilla-ui` Gamepad Lua bridge tests, compiles the real `benilla-app` integration, and type-checks app test code. It deliberately skips the expensive workspace rustdoc pass.

The manual Linux workflow runs workspace Clippy/tests, fork addon harness probes, docs/reference checks and player tests. The manual Windows workflow runs workspace tests and a player link/stack check. These are still required before merge/release. Neither CI lane proves actual SDL/iOS device behavior or rendered UI interaction.

## 1. Packaging

Portable addon source is tracked under:

- `addons/BenillaController/`
- `addons/BenillaMobile/`
- `addons/MinimapMover/`

Install these folders into the runtime `benilla-config/AddOns/` directory. The checked-in source is independent of local saved variables and account configuration. The existing joystick TGA is reused unchanged.

v0.3.0 discovers each addon directory through its matching TOC. `Bindings.xml` is loaded separately after the TOC-listed Lua files and registered with `UiScript::register_addon_bindings`, so addon-defined command handlers are available when bindings are registered. `scripts/check-fork-addons.py` drives the real addon harness and checks clean load/session startup; the controller probe also checks action-slot display and activation for normal, stance and modifier pages.

## 2. Compatibility and integration

### 2.1 BenillaController

The addon retains the eight-button physical layout and three command layers:

- Base layer: 1–8; the native base slots follow the active stance/bonus page.
- LB layer: 9–16; fixed regardless of stance.
- RB layer: 17–24; fixed regardless of stance.

Display and activation share the same slot resolver. The Lua connection check uses the actual bridge name, `Gamepad_IsConnected()`.

The native app polls a normalized controller snapshot and dispatches the 24 addon binding commands through the v0.3.0 binding engine. LB/RB are held modifiers; the command chosen at button-down is latched for the matching release. Trigger-owned face-button input is reserved for the LT pointer/jump/escape layer. The addon remains responsible for action-button visuals, cooldown/count/range state and drag/drop.

### 2.2 Native controller bridge

The app owns the normalized, edge-aware `GamepadSnapshot` and publishes a copy to `UiScript::set_gamepad_state` before FrameXML's `UiTick`. The private script model is not exposed to Bevy systems or Lua callbacks.

Desktop input uses SDL3, supports the selected `--gamepad=N` device and re-enumerates after disconnect/hot-plug. iOS uses GameController's extended gamepad adapter. The Lua bridge exposes the old `Gamepad_*` query/configuration globals and is covered by focused `benilla-ui` tests.

The native adapter also restores these controller actions:

- Left stick: analog movement with radial deadzone and camera-relative facing.
- Right stick: camera look; while LT is held it drives the virtual pointer instead.
- L3: WoW's `TOGGLEAUTORUN`; Plus: world map.
- LT+X: jump; LT+Y: Escape.
- R3: hostile targeting in combat, Smart targeting out of combat; LB+R3 friendly and RB+R3 interactable.
- RT: interact with the active interact target or current selection.
- Virtual pointer: UI/world hit testing and synthetic mouse edges share the normal input pipeline.

These paths compile in the app integration check but still need real-device/runtime validation.

### 2.3 BenillaMobile and touch input

The addon retains its 4×3, 12-slot paging bar, 120-slot reach, sizing/positioning and slash-command configuration. Touch-stick geometry and settings are synchronized through the Lua bridge. The stick is opt-in at the core level until the addon enables it; a connected hardware controller suppresses touch-stick movement ownership.

The app translates raw touch into the existing UI/world pointer pipeline, keeps independent ownership for the movement stick, UI gestures and world camera drag, supports the existing one-second world / three-second UI long-press right-click behavior, and clears stale touch movement when the stick is disabled/unlocked or a physical pad connects. Raw touch activity also refreshes the idle/anti-AFK input timestamp.

The addon harness cannot validate finger tracking, visual layout, touch timing or hardware handoff; those require an actual iOS device.

### 2.4 MinimapMover

The addon retains saved position, lock/unlock/reset commands, cluster movement and the compatibility wrapper around the drag scripts. The harness can check load/session errors, but minimap drag semantics and saved-variable persistence still need a live client check.

## 3. Remaining validation gates

1. Get the PR fast lane green, including app compilation and test-code type-check.
2. Run the full manual Linux and Windows CI workflows.
3. Compile the iOS target and validate the iOS packaging/signing path; the packaging workflow has not yet been re-established on v0.3.0.
4. Run the desktop SDL controller path with a physical pad, including hot-plug, all 24 slots, LT virtual pointer, R3 targeting, RT interaction and movement/camera/swimming.
5. Run on an iPhone/iPad with a controller and without one; verify touch-stick movement, simultaneous UI gestures, long presses, action-bar paging and AFK activity.
6. Verify addon visuals and MinimapMover drag/save behavior in a live client.

Do not treat a green Linux compile or addon harness run as proof of hardware readiness. The point at which the code is ready for the user's hands-on test is after the build/test gates and code-side gaps are closed; live hardware behavior is then the next validation phase.
