# v0.3.0 integration architecture notes

This file records the architectural seams to use when porting the fork's controller/mobile features. It complements [the feature inventory](v0.3.0-feature-inventory.md).

## 1. v0.3.0 facts established from source

The following observations are from the `upgrade/v0.3.0` source tree, not assumptions based on the old fork:

- `crates/benilla-app/src/game_plugins.rs` composes the runtime as an ordered `GamePlugins` group. Its module comment explicitly says registration order is load-bearing.
- The group registers `PlayerPlugin`, then `CursorPlugin`, then `TargetPlugin`; UI script and bindings plugins are registered later in the group. A controller plugin must therefore declare its actual system dependencies rather than rely on incidental registration order.
- `crates/benilla-app/src/player/input.rs` is the current input decoder. It reads `BindingsState` and maps logical `Input` values to movement/camera axes. It does not contain the old fork's `GamepadState` dependency.
- `crates/benilla-app/src/bindings.rs` is the current chord/command engine. It has a `BindingHead`/`BindingTail` pass and the `WorldFrameBindings` leg. Controller integration should feed this engine's existing logical input/binding path rather than implement an unrelated action dispatch system.
- `crates/benilla-app/src/cursor.rs` currently owns hardware cursor rendering and visibility (including the macOS NSCursor path). It is not itself the old fork's virtual pointer position/click state implementation.
- `crates/benilla-app/src/target/mod.rs` exposes the current selection, hovered target/object, pick and interaction structures. The old fork's nearest-target code cannot be copied on the assumption that old target resource names and system signatures still exist.
- `crates/benilla-app/src/lib.rs` exposes `run_with(build, extend)`, an extension hook for plugins on top of a fully built app. This is useful for independent additions, but does not grant access to private `benilla-app` modules or let an external crate modify private player/target internals.

## 2. Recommended ownership boundaries

Keep input acquisition, game semantics and presentation separate:

```text
SDL3 desktop adapter ─┐
                     ├─> ControllerState (normalized, edge-aware)
iOS GameController ──┘              │
                                    ├─> logical binding input ─> BindingsState
                                    ├─> player movement/look adapter ─> Player input
                                    ├─> pointer adapter ─> UI/world hit testing
                                    ├─> targeting/interaction adapter ─> Target subsystem
                                    └─> UI model snapshot ─> Lua globals ─> AddOns
```

The addon should own layout, labels, cooldown/range/count presentation, saved UI settings and touch-stick artwork. Core should own physical device polling, normalized input state, per-finger ownership, world/UI pointer semantics, action dispatch and player movement. Do not let addon Lua reach directly into Bevy ECS resources.

## 3. Integration decisions by current v0.3.0 seam

### 3.1 Plugin registration and scheduling

**Current seam:** `GamePlugins` in `game_plugins.rs`, with an ordered plugin group and schedule tests.

**Port rule:** Add the controller/input plugin at a deliberate location and express ordering with Bevy sets/relations. Polling must happen before any consumer reads the current frame. Script snapshot publication must happen after polling. Binding dispatch, player input, cursor and targeting must have explicit dependencies where they exchange same-frame state.

**Avoid:** Adding a plugin at the end and assuming it runs early enough, or relying only on plugin registration order where a system-level dependency is required.

### 3.2 Logical binding input

**Current seam:** `bindings.rs` owns the command dispatch and logical input state; `player/input.rs` consumes logical `Input` state.

**Port rule:** Adapt controller buttons to the same logical binding path. Preserve press/release edges, UI focus gating, release behavior and modifier-at-press semantics. The controller bar's `Bindings.xml` commands should resolve through the normal binding machinery.

**Avoid:** Calling `UseAction` from a parallel Rust-only dispatch path for every keypress. The addon may use `UseAction` for its visual button surface only if that is intentionally separate from the native controller binding path; the selected action slot must match the icon.

### 3.3 Movement and camera

**Current seam:** `player/input.rs` decodes logical binding state into movement/look commands. The player controller consumes those results; the camera module owns look-session and camera behavior.

**Port rule:** Feed analog axes at the same abstraction level as the current movement decoder or add an explicit analog input field consumed there. Keep one authoritative netting step so direction, speed and swim amounts agree. Feed camera look through the existing camera look-session rather than rotating the camera independently in a second system.

**Avoid:** Restoring the old monolithic player controller or writing player transforms directly from the device poller.

### 3.4 Cursor and virtual pointer

**Current seam:** `cursor.rs` renders the hardware cursor and owns visibility; UI hit testing and target hover use the effective pointer position elsewhere.

**Port rule:** Treat virtual pointer position as a separate input/pointer resource. Make every UI/world hit-test consumer use one shared effective pointer position. Synthetic mouse buttons must enter the same press/release ownership pipeline as physical mouse buttons so that click, drag, UI consumption and focus-loss cleanup remain coherent.

**Avoid:** Editing only the hardware cursor icon and assuming that implements virtual mouse. It does not.

### 3.5 Targeting and interaction

**Current seam:** `target/mod.rs` and its submodules own selection, hover, object hover, pick occlusion and click/interaction flow.

**Port rule:** Implement controller targeting as a thin adapter over current target-selection/interaction APIs. Keep candidate selection rules (enemy, friendly, interactable, Smart/out-of-combat) explicit and separately testable. Right-trigger interaction should submit the current intended interaction target through the current interaction message/API.

**Avoid:** Copying the old `target/scan.rs` or `target/hover.rs` wholesale. Those files contain broad target behavior changes and depend on old structures; first isolate controller-specific behavior from general target-system modifications.

### 3.6 Lua bridge and addon contract

**Old public Lua globals to preserve or intentionally version:**

- `Gamepad_IsConnected()`
- `Gamepad_IsButtonDown(button)`
- `Gamepad_GetAxis(axis)`
- `Gamepad_IsTouchDevice()`
- `Gamepad_SetTouchStick(x, y, radius, travel, enabled, unlocked)`
- `Gamepad_GetTouchStick()`
- `Gamepad_GetTouchStickValue(name)`
- `Gamepad_IsTouchStickEnabled()`
- `Gamepad_IsTouchStickUnlocked()`
- `Gamepad_IsTouchStickActive()`

The first three are the controller state API; the remaining functions configure/query the mobile virtual stick. The old bridge stores the state in the script `Model` and returns scalar/tuple values to Lua. Preserve the API contract unless the addon is updated in the same change.

**Current v0.3.0 seam:** the script model and its installation functions in `benilla-ui`, not direct access to `benilla-app` Bevy resources. Keep platform/device state in the app and publish a copy into the script model.

### 3.7 iOS packaging

Keep packaging independent from the input architecture. Validate the iOS target's current dependency graph and binary output before changing the script. The old script includes more than a build command: app-bundle assembly, optional Data/AddOns staging, profile validation, signing and optional device install. Preserve these operational safeguards unless a current toolchain/API makes them obsolete.

## 4. Open implementation questions

These are not yet decided; resolve them by inspecting the exact v0.3.0 source and testing a small vertical slice:

1. What is the cleanest internal place to register the platform input plugin while preserving the private `GamePlugins` schedule?
2. Which v0.3.0 binding command path can represent the 24 controller slots and modifier-at-press behavior without extending the public key-binding file format unnecessarily?
3. Which pointer resource is authoritative for UI hit testing, world clicks, drag/drop and hover, and how can virtual pointer state enter all of them consistently?
4. Which target-selection entry points can implement R3 Smart/hostile/friendly/interactable selection without reintroducing the old scan algorithm?
5. What is the current iOS target dependency policy and minimum deployment target for `objc2-game-controller`?
6. Can the controller/mobile addons run unmodified on v0.3.0's FrameXML implementation, or do they need a compatibility shim?

## 5. Update protocol

For each ported feature, add a subsection or a linked feature note containing:

- Old behavior and old source locations.
- v0.3.0 files/types/systems used.
- Reused code/assets versus rewritten code.
- State ownership and system ordering.
- Tests added and commands/results.
- Manual test steps and observed results.
- Known deviations and follow-up work.

A feature is not marked complete until its user-visible behavior has been checked, not merely until the crate compiles.
